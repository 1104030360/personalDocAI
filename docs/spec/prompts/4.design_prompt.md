## 4. 強制設計決策

除非上述來源有更新且有明確證據，design 必須保持下列決策不變。

### 4.1 規格草案明定的技術棧與範圍（spec-mandated，不可違反）

- Backend API 使用 **FastAPI**（Python）。
- 儲存使用 **PostgreSQL + pgvector**：照片資訊（文字）、metadata 與向量都存在 PostgreSQL；向量相似度搜尋用 pgvector。
- 圖片理解使用 **VLM**（將照片內容轉成文字與結構化 metadata）。
- **LangChain** 負責 Document 建立、embedding 產生與 vector-store abstraction。
- **LangGraph** 負責 stateful retrieval workflow 與問題類型路由。
- 功能**僅兩項**：上傳照片、自然語言詢問。不得新增任何額外功能。
- 專案定位：**小型、可實際 demo 的 backend**，重點是展示上述技術的整合能力；設計以最簡單可運作為準，不做投機性抽象。

### 4.2 已釐清的規格決策（clarify 階段定案，不得推翻）

#### 資料模型（對應 `erm.dbml` 的 Photo 實體）

- **單一使用者系統**：不建立 User 實體，照片不區分擁有者，詢問時不以使用者過濾。
- **不儲存原始照片檔案**：「照片資訊」僅指 VLM 轉成的文字（`text`），原始照片檔處理完即捨棄；系統任何路徑都不得保留或回傳原始圖檔。
- metadata **僅含固定四欄位**：`category`（照片類別）、`location`（地點/商家）、`items`（物品清單，多值）、`content_time`（內容時間，可空）；VLM 產出不在此清單的資訊**一律捨棄**（曾提出「固定核心＋自由延伸 JSON」與「完全自由 JSON」兩案，均被否決）。
- 時間資訊：`uploaded_at` 由系統於收到照片時自動記錄、必有值；`content_time` 由 VLM 從照片推斷（如收據上的消費日期）、可能為空。
- **「最近」= 詢問當下時間回推 30 天內**；時間性查詢優先以 `content_time` 過濾，為空時以 `uploaded_at` 替代。
- **上傳為同步處理**：上傳完成即代表文字、metadata 與向量皆已儲存；Photo 沒有處理狀態欄位（非同步＋狀態欄位方案已被否決）。
- **embedding 由 `text` 與四個 metadata 欄位合併之內容**（經 LangChain 建立成 Document）產生（「僅文字」方案已被否決）。
- 術語統一：概念一律稱「照片」；「圖片格式」僅指檔案格式時保留；中文稱「向量／embedding 向量」，欄位名維持 `embedding`。

#### 上傳照片功能

- 前置條件：上傳檔案必須為**常見圖片格式（如 JPEG、PNG）**，非圖片格式上傳失敗；**不設檔案大小上限**。
- **VLM 無法理解照片內容（或處理失敗）時，上傳失敗且不儲存任何資料**——不會出現 `text` 為空的照片記錄。
- 上傳成功後系統回應：**照片識別碼＋文字描述＋metadata 四欄位**。

#### 自然語言詢問功能

- 路由**由 LLM 判斷**問題類型：帶明確過濾條件（商家、類別、時間）→ **PostgreSQL metadata search**（例：「有哪些在 Target 拍的收據？」）；語意/內容描述型 → **vector semantic search**（例：「我最近買過什麼飲料？」）。（關鍵字規則式路由與「兩路合併不路由」均被否決。）
- **無法判斷問題類型時，預設走 vector semantic search**。
- **檢索不到任何相關內容時，仍交給 LLM 產生「查無相關照片」的自然語言回覆，且不得編造照片內容**（固定訊息與回傳錯誤兩案被否決）。
- 詢問後，系統將檢索到的內容交給 LLM 產生回答。

### 4.3 待裁決的 design decision（本設計文件必須逐一裁決並附理由）

以下屬技術選型與實作設計，規格未定，設計文件必須明確裁決、標示為 design decision、附一兩句理由，且不得與 4.1/4.2 混淆：

- **VLM 與回答/路由 LLM 的模型選型**（建議優先評估最新 Claude 系列的 vision 與文字能力；以 Context7 查證當前模型 ID 與 API 用法後決定，附來源）。
- **Embedding model 選型與向量維度**（連動 pgvector 欄位維度與 index 選擇，如 HNSW/IVFFlat）。
- Photo 各欄位的**實際 PostgreSQL 型別**：`erm.dbml` 因規格型別清單限制以 string/float 標記，設計須落地為真實型別（如 `items` 用 array 或 JSONB、時間用 timestamp、`embedding` 用 `vector(n)`），並說明與 ERM 的對應。
- `id` 的生成方式。
- **FastAPI 端點設計**：路徑、方法、request/response schema、錯誤格式（涵蓋「操作失敗」的具體 HTTP 語意）。
- **LangGraph workflow 設計**：state schema、節點劃分（路由／metadata search／vector search／生成）、條件邊；金鑰與設定管理方式。
- **metadata search 的條件抽取方式**（如何從自然語言問題產出 SQL 過濾條件，例如 LLM structured output）。
- 專案目錄結構與模組相依方向。

### 4.4 open questions 的處理原則

**規格層面目前沒有未定案項目**：18 項釐清項目全數 Resolved（含補遺輪 3 項），`.feature` 12 條 Rule 全數附 Example、無任何 #TODO。因此不得以「規格未定」為由迴避設計決策。若撰寫過程中發現新歧義：

- 在設計文件中明確標示為 **open question**，說明影響範圍，可附建議選項與傾向，但不得寫成已確認決策；
- 不得自行修改 `.feature`、`erm.dbml` 或 `.clarify/` 來「補上」規格。

## 5. 必做分析

在寫 design 前完成下列內部分析，最終文件只呈現結論與證據。

### 5.1 Spec-to-Design 對照

逐條比對 Gherkin Rule 與設計中的實作位置，標示每條規則由哪個模組負責（FastAPI 端點層 / VLM 整合層 / LangChain 索引層 / LangGraph 節點 / PostgreSQL 存取層）。**不得有規則無人負責。**（規則數以實際檔案為準：自行統計 `docs/spec/features/*.feature` 中的 `Rule:` 數量。）

### 5.2 測試可行性分析

`.feature` 的 Example 將 VLM 理解結果寫在 When 步驟、以資料表描述驗收，隱含「**VLM 與 LLM 在測試中可被 stub**」。設計必須讓 VLM 呼叫、LLM 路由、LLM 回答生成、時鐘（「現在時間」）都可注入替換，並說明各 Example 對應的 stub 點。

### 5.3 約束衝突稽核

檢查設計是否在任何一處違反第 4 節，至少涵蓋：

- 是否引入兩項功能以外的能力（照片瀏覽/刪除、多使用者、帳號認證、對話記憶、前端 UI 等）；
- 是否有任何路徑儲存或回傳原始照片檔；
- metadata 是否只有固定四欄位、清單外資訊是否確實捨棄；
- 是否維持同步處理（無背景工作、無狀態欄位）；
- 路由是否為 LLM 判斷、fallback 是否為 vector search；
- 空檢索結果是否仍經 LLM 且不編造；
- 「最近」是否落實為 30 天與 content_time 優先。

### 5.4 相依順序分析

建立交付切片的相依 DAG（例如：DB schema → 上傳（VLM＋索引）→ 檢索兩路 → LangGraph 路由 → 回答生成），確保每一片交付後系統都可獨立驗證。

### 5.5 外部框架查證

對 LangChain（Document/embedding/PGVector）、LangGraph（StateGraph/條件邊）、pgvector（型別與 index）、FastAPI（上傳檔案處理）與所選模型 API，以 Context7 或官方文件 MCP 查證當前版本的實際用法；查證結論與來源連結記入設計文件的 source inventory。**不得憑記憶寫 API，也不得因工具不可用就捏造查證結果**（工具不可用時明確記錄為限制）。
