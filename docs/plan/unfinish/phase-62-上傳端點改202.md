# Phase 62：上傳端點改 202（階段乙的破壞性變更）

> 🎯 **提醒：這是 side project，不要過度設計。** 只做本文件寫到的事；想「順便多做一點」的時候，答案一律是「不要」。

> 🎯 **一句話目標：** 讓 `POST /photos` 從「等 VLM 看完圖、回 201 ＋ 整份照片內容」
> 改成「把檔案收下、排進佇列、**立刻**回 202 ＋ 一個 `job_id`」——
> 使用者按下上傳之後不必再乾等 2〜5 分鐘。

**為什麼要做這個：** 現在上傳一張照片，瀏覽器會一直轉圈圈直到 VLM 看完圖
（本機 gemma4 實測 64〜88 秒，加上 prompt 變長之後 2〜5 分鐘都有）。
這段時間裡使用者什麼都不能做——不能選下一張、不能去問問題頁。
一次選十張的話更慘：第十張要等前面九張全部看完。
增量五的做法是把「收檔」與「看圖」拆開：HTTP 只做**很快就能做完**的三件事
（檢查格式、把檔案放到暫存區、記一筆任務），然後就回應；看圖交給另一個行程慢慢做。

**這一份是整個增量五最痛的一份**，因為它是**破壞性變更**：
全專案有 **113 個測試函式**會把檔案送進 `POST /photos`——其中大多數預期拿到
201 ＋ 照片內容，全部要逐一檢視（多數要改寫；415 那一小群經檢視後證實不用動）。
下面 §4.6 把每一檔有幾顆、怎麼改，逐條列出來。

---

**新名詞先解釋：**

| 名詞 | 白話解釋 |
|---|---|
| **201 Created**（現在） | HTTP 狀態碼，意思是「**你要的東西已經做好了**，就在回應裡」。現在上傳成功回 201，body 裡有照片 id、AI 寫的文字、建議資料夾…… |
| **202 Accepted**（改成這個） | HTTP 狀態碼，意思是「**我收下了，但還沒做完**」。回應裡沒有結果，只有一張「號碼牌」（`job_id`），要看做完了沒有得再問一次。**收下 ≠ 已入庫**，這是本 phase 最容易誤會的一句話 |
| **破壞性變更（breaking change）** | 改掉之後，原本照舊寫法呼叫的人**一定會壞掉**，而且是明顯地壞掉。202 就是這種——所有寫 `assert status_code == 201` 的地方都會紅 |
| **入列（enqueue）** | 把「要做的事」放進排隊清單。這裡是把 `job_id` 交給佇列，之後由 worker 拿出來做 |
| **broker（中間人）** | 排隊清單住的地方。增量五用 Redis 當 broker（Phase 65／66 才建）。本 phase Redis 還不存在，見 §4.2 |
| **eager（就地執行）** | 「假裝入列，其實當場同步做完」。測試會用它，正式路徑**不用**（理由見 §4.2） |
| **no-op（什麼都不做）** | 一個「有這個函式、但函式裡什麼都沒做」的實作。本 phase 的正式入列器就是它 |
| **staging（暫存區）** | `data/staging/{job_id}.jpg`。HTTP 把上傳的位元組先寫到這裡，worker 之後再從這裡讀。**不把圖塞進 Redis**（design5 §4.1 明文禁止） |
| **JobStore** | 「任務清單」的存放處。Phase 57 已做好，測試用記憶體版、正式用 Redis 版 |
| **uuid4** | 隨機產生的 128 位元識別碼。`uuid4().hex` ＝ 32 個十六進位字元（沒有連字號），例如 `3f2b1c...`。用來當 `job_id` |

### 4.2 入列的抽象：`get_task_dispatcher()`

**問題：** 本 phase 要「把任務丟出去」，但真正接住它的 Celery 要到 **Phase 65** 才存在。

**做法：** 在 `app/dependencies.py` 加一個注入點 `get_task_dispatcher()`，
回傳一個**有 `dispatch()` 方法的物件**（入列器）：拿到之後呼叫 `dispatcher.dispatch(job_id)`。
Phase 65 要換成真 Celery 時，**只改 `get_task_dispatcher()` 這一個函式的本體**
（換成「回傳 `app/celery_app.py` 的 `CeleryDispatcher`」——它的 `dispatch()` 把
job_id 交給 `ingest_task.delay()`；phase-65 §4.5「改動三」有完整程式碼），
router 一個字都不必動。

> 📌 **介面刻意是「有 `dispatch()` 方法的物件」**（`dispatcher.dispatch(job_id)`），
> **不是**把 dispatcher 本身當函式直接呼叫的「可呼叫物」（callable）形狀：
> ① 具名方法對新手比較好讀——`dispatcher.dispatch(job_id)` 這一行自己就說出
>   「把任務派出去」；把物件當函式呼叫的寫法得先回頭查 dispatcher 是什麼才看得懂。
> ② Phase 65 的正式實作 `CeleryDispatcher` 是一個具名類別、住在 `app/celery_app.py`
>   （全系統唯一碰 Celery 的地方——與 `services/ollama_cloud.py` 是「全系統唯一建
>   雲端 Client 的地方」同一種收斂法），具名類別配具名方法最自然。
> ③ 三個實作（下表）與 phase-65 §4.8 測試安全網（`wire_memory_job_store`）的假派工
>   **全部同一個形狀**：Phase 65 換裝時只改 `get_task_dispatcher()` 的函式本體，
>   Protocol／`NoopDispatcher`／router 那一行一個字都不必動。
> 下面的類別都用 `dispatch()` 方法實作這個形狀。

**三個實作（本 phase 寫兩個，第三個是 Phase 65 的）：**

| 實作 | 住哪裡 | 做什麼 | 誰在用 |
|---|---|---|---|
| `NoopDispatcher` | `app/dependencies.py` | 什麼都不做，只留一行 log | **本 phase 的正式路徑**（Phase 62〜64） |
| `EagerDispatcher` | `tests/fakes.py` | 就地把 `run_ingest_job` 跑完 | 測試（要「入列＝當場做完」的情境用） |
| `CeleryDispatcher` | `app/celery_app.py` | `ingest_task.delay(job_id)` | Phase 65 之後的正式路徑 |

**為什麼正式路徑選 no-op 而不是 eager（這是本 phase 唯一的取捨題）：**

1. **eager 會變成「回 202 卻卡 5 分鐘」。** 正式路徑若就地跑完，
   瀏覽器按下上傳一樣要等 VLM 看完圖，只是狀態碼從 201 變成 202——
   **比現在更難懂**（使用者看到「已收下」卻還在轉圈圈）。
   design5 §0 的第一條「禁止」講的正是這種半套。
2. **eager 會在 uvicorn 的請求執行緒裡跑真模型。** Phase 48 已經踩過：
   本機 gemma4 並行看圖把 db container 壓垮，postmaster 花兩分鐘才殺得掉子行程。
3. **no-op 讓「還沒接上」這件事是明擺著的**，不是藏起來的。
   Phase 65 接上 Celery 那一刻，行為的改變是「照片開始真的入庫」，
   非常好驗；而不是「本來就會入庫，只是換了一條路」那種說不清楚的改動。

> 🚨 **這件事一定要記住，不然你會以為系統壞了**
>
> **Phase 62〜64 期間，手動用瀏覽器上傳照片，照片「不會」真的入庫。**
> 你會看到瀏覽器很快收到 202（這是對的），但待決定頁一直是空的、
> `data/photos/` 也不會多檔案，只有 `data/staging/` 會慢慢累積暫存檔。
> **這是預期行為，不是 bug。** 因為正式的入列器現在是 no-op，
> 沒有任何人會去把 staging 裡的檔案撿起來看圖。
>
> **要到 Phase 65（Celery ＋ RedisJobStore）與 Phase 66（compose 加 redis／worker）
> 做完，系統才會真的動起來。** 在那之前，「照片真的入庫了嗎」只有
> `pytest` 驗得出來（測試自己扮演 worker 呼叫 `run_ingest_job`）。

```python
# ---------------- 入庫任務的入列器（增量五 Phase 62）----------------
#
# 「入列」＝把一個 job_id 丟出去，讓別人去做。誰接住它，Phase 62〜64 與
# Phase 65 之後是不一樣的：
#   Phase 62〜64：NoopDispatcher（沒有人接住——Celery 還沒建，這是**預期**的）
#   Phase 65 起  ：get_task_dispatcher() 本體換成「回傳 app/celery_app.py 的
#                  CeleryDispatcher」，它的 dispatch() 把 job_id 交給
#                  ingest_task.delay()（丟進 Redis，由 worker 容器接住）
# 換的時候只改 get_task_dispatcher() 這一個函式，router 一個字都不動。


class TaskDispatcher(Protocol):
    """把一筆入庫任務丟出去的入列器。介面只有一個具名方法 dispatch()。

    用法：dispatcher.dispatch(job_id)。**不是**把 dispatcher 本身當函式直接呼叫——
    具名方法讓 router 那一行自己會說話；Phase 65 的正式實作 CeleryDispatcher
    （住在 app/celery_app.py，全系統唯一碰 Celery 的地方）與 Phase 65 測試安全網
    的假派工也都有同一個 dispatch() 方法，三邊同形、換裝時誰都不必動。

    參數**只有 job_id**：檔案內容在 data/staging/、其餘欄位在 JobStore，
    佇列裡只放一個字串（design5.md §4.1 明文禁止把影像位元組當任務參數）。
    """

    def dispatch(self, job_id: str) -> None: ...


class NoopDispatcher:
    """什麼都不做的入列器（Phase 62〜64 的正式實作）。

    ⚠ 這代表**照片不會真的入庫**——Celery 要到 Phase 65 才存在。
    刻意不在這裡「就地跑完」（eager）：那會讓 HTTP 回了 202 卻仍然卡住
    2〜5 分鐘等 VLM，比同步的 201 更難懂，也會把真模型的推論
    塞進 uvicorn 的請求執行緒（Phase 48 已踩過會把資料庫壓垮）。

    log 留 INFO 一行：手動測試時看得到「有收下、但沒有人接手」。
    """

    def dispatch(self, job_id: str) -> None:
        logger.info(
            "任務已建立但尚未入列（Phase 65 接上 Celery 之前這是預期行為）：job_id=%s",
            job_id,
        )


def get_task_dispatcher() -> TaskDispatcher:
    """給 router 的入列器。

    Phase 65 要接上 Celery 時，把這個函式的**本體**換成：
    「函式內 `from app.celery_app import CeleryDispatcher`，
    回傳 `CeleryDispatcher()`」——它的 dispatch() 把 job_id 交給
    `ingest_task.delay()`。完整程式碼在 phase-65 §4.5「改動三」，
    **就改這一個函式**。
    """
    return NoopDispatcher()
```

```python
class EagerDispatcher:
    """就地把任務跑完的入列器（測試用；eager ＝ 同步、當場做完）。

    正式路徑刻意**不用**這個（見 app/dependencies.py 的 NoopDispatcher docstring）。
    給「想要 POST 完照片就已經在資料庫裡」的測試情境用：
    換上這一個，router 一呼叫入列器，任務就當場跑完。

    形狀與 TaskDispatcher 一樣有 dispatch() 方法，
    所以掛上 dependency_overrides 之後 router 那句 dispatcher.dispatch(job_id) 照常能呼叫。

    四個協作者由建構子帶進來（不自己去 dependencies 拿）：
    測試想換成「會爆炸的 embeddings」之類的壞假件時，直接換參數就好。
    """

    def __init__(self, *, store, vlm, embeddings, now) -> None:
        self._store = store
        self._vlm = vlm
        self._embeddings = embeddings
        self._now = now

    def dispatch(self, job_id: str) -> None:
        from app.services.ingest_job import run_ingest_job

        run_ingest_job(
            job_id,
            store=self._store,
            vlm=self._vlm,
            embeddings=self._embeddings,
            now=self._now,
        )
```

```python
def _收件箱照片ids() -> list[int]:
    """收件箱裡現在有哪些照片 id（新的在前）。"""
    inbox = next(f for f in _repo.list_folders() if f["is_inbox"])
    return [row["id"] for row in _repo.list_photos_in_folder(inbox["id"])]


def 上傳並跑完任務(
    client,
    *,
    payload: bytes | None = None,
    filename: str = "a.png",
    content_type: str = "image/png",
) -> dict:
    """POST /photos → 斷言 202 → 把那個任務跑完 → 回報結果。

    回傳一個字典，四個鍵：
      job_id    ：202 給的號碼牌
      response  ：POST 的原始回應（要驗 202 的 body 時用得到）
      job       ：跑完之後的任務狀態；**成功時是 None**（成功＝job 被刪掉）
      photo_ids ：這一次新進收件箱的照片 id（單圖一個、PDF 可能多個，由小到大）

    photo_ids 為什麼要用「前後比對」算出來，不是從 job 讀：
    契約備忘 §3.1 說「成功 ＝ delete(job_id)」，所以任務跑完之後那筆 job
    連同它的 photo_ids 一起消失了。改用「跑之前收件箱有誰、跑之後多了誰」，
    對單圖與 PDF 都成立，也不必為此新增任何 repository 函式。
    """
    if payload is None:
        payload = make_png_bytes()

    前 = set(_收件箱照片ids())
    response = client.post(
        "/photos", files={"file": (filename, payload, content_type)}
    )
    assert response.status_code == 202, response.text
    job_id = response.json()["job_id"]

    跑完任務(job_id)

    新增 = sorted(i for i in _收件箱照片ids() if i not in 前)
    return {
        "job_id": job_id,
        "response": response,
        "job": 目前的任務清單().get(job_id),
        "photo_ids": 新增,
    }

        "PDF 請改用 上傳並跑完任務()"
    )
```

```python
def _accept_upload(
    upload_bytes: bytes,
    *,
    filename: str,
    content_type: str,
    store: JobStore,
    dispatcher: TaskDispatcher,
    source: str,
) -> IngestAcceptedResponse:
    """把「收下的檔」變成一筆排隊中的任務，回 202 的內容。

    ★★ 順序鐵律（把 ①〜④ 的順序調換 = 製造 bug）★★
      ① 先產 job_id      ── staging 的檔名要用它，所以它得最先決定
      ② 再寫 staging     ── 檔案先落地
      ③ 再建 job         ── 任務清單上才看得到這一筆
      ④ 最後才入列       ── 有人來做的那一刻，前面兩樣一定都準備好了

    反過來做（先入列再寫 staging）會出現「worker 已經開始做、但檔案還沒寫完」
    的競爭——worker 讀到半個檔或根本讀不到檔，看起來像隨機失敗。

    ②③④ 任何一步失敗 → **把 staging 與 job 都清掉**再把原始錯誤往外丟
    （框架會回 500，log 留 traceback）。design5.md §8 第 8 列講的就是這件事：
    Redis 掛掉的時候，不要在磁碟上留一個沒有人會來撿的暫存檔。
    """
    # uuid4().hex ＝ 32 個十六進位字元。為什麼不用資料庫序號（見 §7 陷阱 3）：
    # 這一刻我們**刻意不碰資料庫**，而序號要先 INSERT 才拿得到；
    # 而且 job 住在 Redis／記憶體，本來就沒有序號這種東西。
    job_id = uuid4().hex

    try:
        staging_service.save_staging(job_id, content_type, upload_bytes)
        store.create(
            job_id=job_id,
            filename=filename,
            content_type=content_type,
            # D14：把「現在開關撥在哪」拍成快照存進任務。worker 是另一個行程，
            # 讀不到這個行程記憶體裡的 config.AI_BACKEND；而且使用者中途把開關
            # 撥回本機時，已經排隊的任務不該跟著改道。
            ai_backend=config.AI_BACKEND,
            source=source,
        )
        dispatcher.dispatch(job_id)
    except Exception:
        # 兩個清理動作都必須「本來就不在也不炸」：
        #   remove_staging 比照 storage_service.remove_if_exists
        #     （save_staging 若寫到一半就炸，磁碟上可能有半個檔，也一起清）
        #   store.delete  對不存在的 job_id 要安靜（見 §4.0 的檢查項）
        # 清掉 job 的理由：入列失敗卻留著一筆 queued，進度面板會出現一列
        # 永遠不會動的幽靈任務，而且它連 dismiss 都按不掉（只准 dismiss failed）。
        staging_service.remove_staging(job_id, content_type)
        store.delete(job_id)
        raise

    logger.info(
        "已受理入庫任務：job_id=%s filename=%s content_type=%s source=%s backend=%s",
        job_id, filename, content_type, source, config.AI_BACKEND,
    )
    return IngestAcceptedResponse(
        job_id=job_id, filename=filename, content_type=content_type
    )
```

```python
def _upload(context, client, filename="photo.png", content_type="image/png",
            payload=PNG_BYTES):
    """When 步驟：收下檔案（202）**並且把那個任務跑完**。

    增量五把上傳拆成兩段：HTTP 只收下（202），worker 才真的入庫。
    規格檔（唯讀，Phase 72 才准改）寫的是「上傳照片後，系統儲存……」——
    描述的是使用者看得到的最終結果，所以 binder 這一層要把兩段接起來，
    Then 才看得到照片。少了「跑完任務」那一步，每一條 Then 都會變成
    「系統儲存的照片數量為 0」（design5.md §9 最後一段）。

    415 那一條 Rule 走另一條路：連 202 都拿不到，自然也沒有任務可跑。
    """
    app.dependency_overrides[get_vlm] = lambda: FakeVLM(context["understanding"])

    context["photo_ids"] = []
    context["job"] = None
    照片數_收檔前 = photo_repository.count_photos()
    response = client.post(
        "/photos", files={"file": (filename, payload, content_type)}
    )
    context["response"] = response
    if response.status_code != 202:
        return                      # 格式不對（415）：Then「操作失敗」會驗它

    # design5.md §9 的第 2 步：202 只是「收下了」，這一刻 photo 表一列都沒有多
    assert photo_repository.count_photos() == 照片數_收檔前

    job_id = response.json()["job_id"]
    前 = set(_收件箱照片ids())
    跑完任務(job_id)
    context["job"] = 目前的任務清單().get(job_id)
    context["photo_ids"] = sorted(i for i in _收件箱照片ids() if i not in 前)


def _photo_id(context) -> int:

        f"job 狀態：{context['job']}"

def _stored_photo(context) -> dict:
```

```python
def 操作失敗(context):
    """規格的「操作失敗」在增量五有兩種長相（規格檔 Phase 72 才准改）：

    - 非圖片格式：HTTP 當場 415——維持原本的斷言。

      改驗「任務最後是 failed、而且沒有任何照片進收件箱」。

    Phase 72 會把「VLM 無法理解」那條 Example 的 `Then 操作失敗` 從規格裡刪掉
    （202 不是失敗，失敗的是背景分析），到時 202 這個分支自然沒人再走；
    415 那條 Example 仍然用本 step，所以 Phase 72 也**不會**刪這個函式
    （phase-72 §4.3 已對齊這裡的寫法）。
    """
    response = context["response"]

        assert context["job"] is not None and context["job"]["status"] == "failed", (
            f"202 之後規格說的「操作失敗」＝任務失敗，實際 job：{context['job']}"
        )
        assert context["photo_ids"] == [], "失敗的上傳不可以有照片進收件箱"
    else:
        assert response.status_code >= 400, response.text
```

## 7. 常見陷阱

1. **以為 202 就是「上傳成功、照片存好了」。**
   這是本 phase 最大的坑，而且會以很多種面貌出現：手動測試時以為系統壞了、
   寫測試時 `POST` 完直接斷言 `count_photos() == 1`、
   前端（Phase 68）以為可以立刻拿 `photo_id` 去開彈窗。
   **202 只代表「檔案收下了、排進佇列了」**，照片要等 worker 做完才存在。
   驗收清單裡那一顆 `test_202當下資料庫還沒有那一列` 就是釘死這句話用的。

2. **Phase 62〜64 期間手動上傳，照片不會入庫——不是壞掉。**
   正式的入列器是 `NoopDispatcher`（什麼都不做），因為 Celery 要 Phase 65 才建。
   症狀：202 很快回來、`data/staging/` 檔案越積越多、待決定頁永遠是空的。
   **這是設計，不是 bug。** 忍不住想「乾脆讓正式路徑也 eager」的時候，
   回頭讀 §4.2 的兩個理由（會變成回 202 卻卡 5 分鐘、會把 db 壓垮）。

3. **想用資料庫序號當 `job_id`。**
   行不通，而且是三重的行不通：
   ① staging 的檔名要用 job_id，而檔案要在建 job 之前就寫好；
   ② 序號要先 INSERT 才拿得到，但這一刻我們**刻意不碰資料庫**
      （design5 §4.2：202 當下 photo 表列數不變）；
   ③ job 住在 Redis／記憶體，那裡根本沒有序號這種東西。
   用 `uuid4().hex`：32 個十六進位字元，可以直接當檔名、直接當 Redis key，不必跳脫。

4. **忘了刪失敗路徑的 staging。**
   `dispatcher.dispatch(job_id)` 炸掉時（Redis 掛了），staging 檔已經寫在磁碟上了。
   不刪的話那個檔案要等 24 小時掃把（Phase 58）才會被清掉，中間就是垃圾。
   `test_入列失敗時回500而且staging與任務都不留` 守這件事。
   順帶：**`store.delete()` 也要刪**——留著一筆 queued 卻沒有人會做，
   進度面板（Phase 67）會出現一列永遠不動的幽靈，而且連 × 都按不掉
   （Phase 64 只准 dismiss `failed`）。

5. **`status_code=202` 忘了寫在裝飾器上。**
   FastAPI 的成功狀態碼是由 `@router.post(..., status_code=202)` 決定的，
   不是由 `return` 的內容決定。忘了寫就會回 200（不是 201，因為 201 是原本寫死的），
   而且測試的錯誤訊息只會說「200 != 202」，看不出是裝飾器少了一個參數。
   同一行的 `response_model=UploadResponse | PdfUploadResponse` **也一定要換掉**，
   否則 FastAPI 會拿 `IngestAcceptedResponse` 去驗 `UploadResponse` 的形狀，直接 500。

6. **測試忘了跑任務就斷言照片存在。**
   症狀非常一致：`assert photo_repository.count_photos() == 1` 得到 0，
   或 `fetch_photo(...)` 回 `None` 之後 `TypeError: 'NoneType' object is not subscriptable`。
   看到這兩個症狀，第一個要檢查的就是「這顆測試有沒有呼叫 `跑完任務()`」。

7. **`caplog` 的計數被那一行新 log 弄歪（只影響 `test_ai_timing_log.py`）。**
   202 那一段會多印一行 `已受理入庫任務：job_id=…`。
   那一檔靠 `caplog.messages` 逐則過濾計數，所以 POST 之後、跑任務之前
   一定要 `caplog.clear()`。忘了的話錯誤訊息會是「1 != 2」之類，
   看起來像 `ai_timing` 壞了，其實只是多了一行不相干的 log。

8. **`FakeVLM` 的 `.calls` 對不上——因為換了實例。**
   `app.dependency_overrides[get_vlm] = lambda: FakeVLM(收據理解)` 每次呼叫都**新建一個**。
   要驗 `.calls`／`.last_folders`／`.last_entities` 的測試必須先綁一個實例：
   ```python
   vlm = FakeVLM(收據理解)
   app.dependency_overrides[get_vlm] = lambda: vlm     # 永遠是同一個
   ```
   既有那幾顆（`test_pdf_upload.py`、`test_upload_design_rules.py`、`test_ai_timing_log.py`）
   本來就是這樣寫的，改寫時**不要順手改成 `lambda: FakeVLM(...)`**。

9. **改到 `docs/spec/features/上傳照片.feature`。**
   規格檔唯讀，Phase 72（★ G3 產品負責人明示核准解禁）才准動。
   本 phase 只改 binder。改完記得 `git status --short -- docs/spec/` 確認沒有輸出。

    `photos._ingest_image()`，`test_camera_endpoints.py` 的 34 顆應該**全綠**。
    如果它們紅了，代表你動到了不該動的東西。

11. **順手把 `_ingest_image()` 也一起刪掉。**
