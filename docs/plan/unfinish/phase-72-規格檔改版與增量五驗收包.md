> 🎯 **提醒：這是 side project，不要過度設計。** 只做本文件寫到的事；想「順便多做一點」的時候，答案一律是「不要」。

```text
║                                                                              ║
║  要等產品負責人**親口／親手**說出類似這句話：                                 ║
```

> 🎯 **一句話目標：** 產品負責人核准解禁之後，把**四份** `.feature`
> （不是三份——`歸類照片.feature` 那個「等」字底下藏著 `瀏覽檔案櫃.feature`）
> 改成「收下 ≠ 已入庫」的說法，驗收 BDD binder 仍然全綠，
> 最後產出一份給產品負責人逐條勾的**增量五驗收包**，並把 22 份計畫檔與 `CLAUDE.md` 收乾淨。

**為什麼要做這個：**

規格檔（`.feature`）是**唯一**同時被「人讀」與「機器跑」的文件。
`tests/integration/test_upload_feature.py` 第 30 行是這樣寫的：

```python
scenarios("../../docs/spec/features/上傳照片.feature")
```

——**直接把規格原檔當測試跑**，不複製、不改寫。
所以規格檔一旦與實際行為對不上，會出現最糟的一種狀況：**測試是綠的，但規格在說謊**。

現在規格上寫著「上傳照片**後**，系統儲存照片資訊」。
增量五之後這句話是假的：上傳後系統只是**收下檔案**（HTTP 202），
照片要等 worker 在背景分析成功才存在。差別可能是好幾分鐘。
半年後有人照著規格看程式，會以為「上傳回來了 ＝ 資料庫有了」，然後寫出錯的東西。

**新名詞先解釋：**

| 名詞 | 白話解釋 |
|---|---|
| **解禁**（解除唯讀） | `docs/spec/` 平常一個字都不准改。產品負責人明示核准之後，**只有他核准的那個範圍**可以改，其餘仍然唯讀 |
| **Rule 行 vs Then 行** | Gherkin 檔案裡 `Rule:` 開頭那一行只是**分組標題**，不會綁到任何程式碼；`Given/When/Then/And` 開頭的才是**步驟**，每一句都要在 binder 裡找得到對應的函式。**這個差別是本 phase 最重要的一件事**（§4.1） |
| **binder**（綁定檔） | 把規格的中文句子接到 Python 程式碼的那個檔。本專案有三份：`test_upload_feature.py`／`test_ask_feature.py`／`test_camera_feature.py` |
| **`#TODO` Rule** | 規格寫了規則、但**沒有給例子**。pytest-bdd 不會為它產生任何測試。本專案用它來記錄「這條規則是真的，只是規格文本沒給可驗的例子」 |
| **驗收包** | 一份給產品負責人**逐條勾**的清單。他照著點一遍、看一遍，勾完就是「這個增量做完了」。實作者不能自己勾人的那幾條 |
| **歸檔** | 把 `docs/plan/unfinish/`（還沒做完）的計畫檔搬到 `finish/`（做完了）。本專案的慣例是**隨 commit 執行**，不提前搬 |

## 4. 實作步驟

### 4.1 動筆前先搞懂一件事：Rule 行是自由的，步驟行不是

這是本 phase 唯一的技術重點，搞懂它整件事就變簡單了。

```text
  ┌─────────────────────────────────────────────────────────────────┐
  │  Feature: 上傳照片                    ← 自由（只是標題與說明）   │
  │    使用者透過 FastAPI 上傳照片。      ← 自由                     │
  │                                                                 │
  │    Rule: 上傳照片後，系統儲存照片資訊  ← ★ 自由！**不綁程式碼**  │
  │                                          pytest-bdd 只拿它分組   │
  │                                                                 │
  │      Example: 上傳 Target 收據照片…   ← 半自由（會變測試函式名）  │
  │                                          改了＝測試改名，無害     │
  │                                                                 │
  │        When 使用者上傳一張照片，VLM… ← ⛔ **綁死**               │
  │        Then 照片的文字描述為 "…"      ← ⛔ **綁死**              │
  │            └─ 這兩句要逐字對得上 binder 裡的                     │
  │               @when(parsers.parse('…')) ／ @then(parsers.parse('…'))│
  │               差一個字就 StepDefinitionNotFoundError（收集階段炸） │
  └─────────────────────────────────────────────────────────────────┘
```

**所以本 phase 的改法是：**

- 「哪些話已經變成假的」→ 絕大多數都寫在 **Rule 行**（那是規格在**陳述規則**的地方）→ **放心改**。
- 步驟行只有**兩處**非改不可（都在 §4.3），而且兩處都是**刪掉**一句，不是改寫成新句子
  ——刪掉不會產生「找不到 step」的問題。

- [ ] 先自己驗證一次這個說法（30 秒，不改檔）：

```bash
grep -c "^  Rule:" docs/spec/features/上傳照片.feature      # 18 條 Rule（15 條有 Example ＋ 3 條 #TODO）
grep -c "Rule" /tmp/phase72-upload-steps.txt                # 0——binder 的 step 裝飾器裡一個 Rule 都沒有
```

  預期：第一行印 **18**、第二行印 **0**。
  （binder 檔頭的 docstring 寫「15 條有例子的 Rule」——那是**有 Example 的**條數；
  `grep -c "^  Rule:"` 數的是**全部** Rule 行，含最後三條 `#TODO`，所以是 18。）
  binder 完全不認識 `Rule:`，所以改 Rule 行不可能弄壞測試。

### 4.2 檔頭核准紀錄的格式（四份都要，一字不改地照抄）

`docs/spec/` 是唯讀規格區。沒有這段紀錄，下一個人 `git log` 看到規格被改，
只能推論「有人違規動了唯讀檔」。

既有的紀錄長這樣（`docs/spec/features/上傳照片.feature` 第 2〜9 行，現況原文；
另一筆解禁紀錄在 `自然語言詢問.feature` 檔頭第 6〜10 行，格式相同）：

```text
# 2026-08-20 依 docs/design/design1.md 正式改版（產品負責人核准解除唯讀）：
#   1. 上傳當下照片一律先歸到「未分類」，VLM 給的類別只是建議，由使用者確認後才定案
#   2. 系統改為保留原始照片檔與縮圖（推翻「不含原始照片檔」的舊定案）
#   3. 成功回應加上所屬資料夾、建議資料夾與完整資料夾清單
# 2026-08-21 依 docs/design/design3.md D7 追加一條 Rule（產品負責人核准解除唯讀）：
#   4. 接受的檔案格式加上 PDF——一頁當成一張照片，多頁就多張
# 2026-08-22 依 docs/design/design3.md D8／D12／D13 追加實體與待辦建議（產品負責人指示補 features）：
#   5. 同一輪 VLM 另給實體建議 0 或 1 個、待辦建議 0 或 1 筆；都只出現在回應，人確認才落庫
```

## 7. 常見陷阱

1. **在 G3 之前就「先改好放著」。**
   最嚴重的一條。design5 §10 最後一句寫得很清楚：
   「未核准前：實作可以先讓測試 binder 對齊新 API，但**不要改** `docs/spec/features/`」。
   理由不是儀式感——規格區是唯讀的，改了就進了 `git diff`，
   下一個人看到的是「有人動了唯讀檔」，而不是「有人拿到核准後動了唯讀檔」。
   要證明是後者，只有一個辦法：**核准在前、改動在後，而且檔頭有紀錄**。

2. **改到步驟行（`Given/When/Then/And`）。**
   症狀：`pytest` 在**收集階段**就炸，訊息是
   `StepDefinitionNotFoundError: Step definition is not found: When "…"`，
   而且會把找不到的那句中文直接印出來。
   修法：對照 `/tmp/phase72-upload-steps.txt`，把句子改回 binder 裡有的那一句。
   **本 phase 只有三處碰步驟行**：刪 `Then 操作失敗`、`And` 改 `Then`、
   `瀏覽檔案櫃.feature` 那個沒有 binder 的 `Then` 參數。其他一律不准碰。

3. **以為 `瀏覽檔案櫃.feature` 改了會有測試保護。**
   **它沒有 binder。** 全專案只有三份 binder（`grep -rn "scenarios(" tests/` 可以確認）。
   `歸類照片`／`釘選實體`／`建立待辦`／`瀏覽檔案櫃` 四份**從來沒有被執行過**。
   所以改它們零風險，也**零保護**——改壞了不會有紅燈，只能靠自己讀一遍。

4. **只改 design5 §10 字面提到的「三份」。**
   §10 第三列寫的是「`歸類照片.feature` **等**」。逐行讀過之後
   `瀏覽檔案櫃.feature` 第 8〜11 行那條（「開啟瀏覽頁時，目前分頁為待決定」）
   在 D1 之後是**完全反過來的**——瀏覽頁根本沒有待決定分頁了。
   漏掉它，規格就會自己跟自己打架。

5. **順手把 `釘選實體.feature` 或 `建立待辦.feature` 也「更新一下」。**
   逐行讀過：這兩份**沒有任何一句**提到入口、路徑、或「何時算存好」。
   核准的範圍是 §10 那幾件事，沒被核准的部分**仍然唯讀**。
   （這與 Phase 51 §3「明確不做」第 2 列是同一條原則。）

6. **把「回應」統一改成「照片的」。**
   看起來很合理（202 之後回應裡確實沒那些東西），但那幾句
   `Then 回應的文字描述為 "…"`／`Then 回應的建議資料夾如下` **全部是步驟行**，
   改了就找不到 step。
   正確做法是只改**Rule 行**的用詞（「回應」→「提供」），
   步驟行留給 Phase 62 已經對齊好的 binder 去解釋。
   這是本 phase 刻意留下的**措辭債**，記在驗收包的「已知限制」裡。

7. **顆數變了。**
   本 phase 新加的兩條 Rule 都掛 `#TODO`（沒有 Example）→ pytest-bdd 不會產生 scenario
   → **顆數一顆都不該變**。
   變多了：你不小心給新 Rule 寫了 Example。變少了：某個 Example 被你改壞、
   或 Example 名重複了（pytest-bdd 會用 Example 名產生函式名，重名會蓋掉）。

8. **自己勾驗收包的 B〜E 段。**
   A 段是自動化跑出來的數字，實作者勾沒問題。
   B〜E 是**人的動作**——就算你自己在瀏覽器點過三遍，也不算。
   （這與 Phase 44 §8 陷阱 1 是同一條原則：實作者不得自行把閘門勾過。）

9. **提前 `git mv` 把 22 份計畫檔搬進 `finish/`。**
   `git mv` 會直接 stage，與「先不 commit」的既有指示衝突，
   而且萬一產品負責人在驗收時要求改某個 phase，那份計畫檔已經被標記成「完成」了。
   §4.9 只列清單與指令，動作**隨 commit 執行**。

10. **`CLAUDE.md` 貼了新段落卻沒清舊敘述。**
    最容易漏的兩處：「端點 19→20」附近那句「端點恰 20」，

    ——留在文件裡的**歷史敘述**（「增量四把端點從 19 加到 20」）是對的、要保留；
    要改的是任何一句在描述**現況**的地方。
