## 1. 實作邏輯（為什麼要繞 5434 這一圈）

brew 的 PostgreSQL 現在佔著 **5433**，兩個服務不能同時聽同一個埠。
更重要的是——**在還沒證明資料搬得對之前，舊的那份必須完好無缺地繼續活著**。

```text
      brew @17 :5433  ●running（正本，全程不動）
            │  Phase 45 的 pg_dump -Fc
            ▼
      ~/…遷移前.dump
            │  Phase 46 的 pg_restore
            ▼
      docker db :5434 ●running（複本）
            │
      ★★★ 閘門 G2：兩邊快照 diff
            │
     ┌──────┴──────┐
   沒輸出         有輸出
  → Phase 47    → 停在 5434，brew 繼續服務
```

所以先借 5434 這個空埠把新的養起來、對完帳，再挑時間把舊的關掉（Phase 47）。

**本階段零產品程式碼變更、零新增自動化測試**——動到的全是設定檔與終端機操作。

### 2.2 起 db

- [ ] `docker compose up -d db`（第一次會下載 `pgvector/pgvector:pg17` 映像）
- [ ] 等 `docker compose ps` 變 `Up … (healthy)`
- [ ] ⚠ **剛 healthy 就連可能被拒**：官方映像會先起一個「只聽 Unix socket」的暫時伺服器跑 init，
      這段期間 `pg_isready` 就已回報成功。判斷方式：log 裡
      `database system is ready to accept connections` 要出現**兩次**，第二次才是正式的

      （**`-h 127.0.0.1` 不能省**——沒有 `-h` 會走 Unix socket 連到 brew 那一套）

### 2.3 灌正式庫

      而且照樣回傳 0——不能只憑「指令跑完了」判斷成功）

## 3. 明確不做

| 不做 | 為什麼 |
|---|---|
| 在 `compose.yaml` 寫 `app` | `Dockerfile` 還不存在（Phase 48） |
| 用 5433 | brew 還佔著，這一輪一定是 5434 |
| `docker compose down -v` | `-v` 刪 volume ＝ 刪掉剛灌好的庫 |
| 對正式庫跑 `db/schema.sql` | 開頭是 `DROP TABLE`，只有測試庫可以 |
| `brew services stop postgresql@17` | Phase 47，而且要 G2 過了才准 |
| 改 `.env` 或 `tests/conftest.py` | Phase 47。這一輪 host 上一切還連 brew 的 5433 |
| 碰 `postgresql@14`（5432） | 別的專案的 |
| `network_mode: host` | Docker Desktop on Mac 行為不同，Compose 服務名 DNS 會失效 |
