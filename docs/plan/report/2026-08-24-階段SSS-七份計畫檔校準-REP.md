顆數鏈（本次核對後的正確版）：

358（P37 收）→ 365（P38）→ 373（P41）→ 379（P42）→ 384（P43）

> 💡 這裡踩到一個小坑值得記：macOS 的 BSD `sed` **不支援 `\b`**（word boundary），

> 改用 `perl -i -pe 's/(?<![0-9])387(?![0-9])/402/g'` 才對。

### C4　鏡頭 QR 的 IP 判準：「不可以是 `172.`」→ **「逐字等於 `en0`」**

**這一項是本次校準裡唯一可能造成誤判的技術性錯誤，值得完整記錄。**

| | 內容 |
|---|---|
| **計畫原文** | `phase-50` §4.3／§6／§7 陷阱 3、11：「QR 網址**必須是 `https://192.168.…`、不可以是 `172.…`**」（理由：容器裡猜 IP 會猜到 Docker 網橋的 `172.x`） |
| **實測事實** | `ipconfig getifaddr en0` ＝ **`172.29.93.122`** |
| **為什麼原判準是錯的** | `172.16.0.0/12` 是 RFC 1918 的合法私有網段，**這是真的區網 IP**（很可能是熱點或公司網路），不是 Docker 網橋。更糟的是 Docker 預設的網段池正好也在 `172.17`〜`172.31`——`172.29` 就落在裡面。**光看前綴，真區網與 Docker 內部網段根本分不出來** |
| **改法** | 判準改成唯一可靠的那個：**QR 裡的 host 必須逐字等於 `ipconfig getifaddr en0` 的輸出**。這在任何網段下都成立（192.168／172.20／10.x 都一樣），而且不必去背 Docker 用哪些網段。§4.3 說明框、§4.5 第 ⑨ 條、§6 驗收清單、§7 陷阱 11 四處同步改完 |

### C5　mkcert 憑證的 SAN 是**舊 IP**

| | 內容 |
|---|---|
| **怎麼發現的** | 校準 C4 時順手驗了一下憑證：`openssl x509 -in certs/cert.pem -noout -text \| grep -A2 "Subject Alternative Name"` → `DNS:localhost, IP:172.20.10.6, IP:127.0.0.1` |
| **事實** | 憑證簽的是 `172.20.10.6`（舊 IP），現在的 en0 是 `172.29.93.122`——**對不上** |
| **影響** | 對 45〜49 的驗收（全走 `127.0.0.1`）**沒有影響**；但 Phase 50 的手機真機驗收**一定會被 Safari 擋**，而錯誤訊息看起來像「網路怪怪的」，極難聯想到憑證 |
| **改法** | `phase-48` §2 的前置條件從「憑證檔案存在」升級為「**SAN 要含現在的 en0 IP**」，附檢查指令與重簽指令；`phase-50` §4.3 在真機驗收前也加了同一道檢查（重簽後要 `docker compose restart app`——HTTPS 行程啟動時就把憑證讀進記憶體了） |

### 其餘兩處小校準

- **`phase-46` §2**：開工當下 `docker version` 只有 Client（Docker Desktop 沒開）。
  補上從終端機啟動的做法與**輪詢等待**的寫法
  （`until docker info >/dev/null 2>&1; do sleep 3; done`，比盲等 30 秒可靠）。
- **`phase-47` §4.5**：計畫寫的驗證指令是 `uvicorn app.main:app --reload --port 8000` ＋
  `curl http://…`；但開工當下 host 上跑的那支是 **HTTPS 版**（`--host 0.0.0.0 --ssl-*`）。
  補一段說明「兩種都行，**但 `curl` 的協定要跟著換**」——用 `http://` 打 HTTPS 服務會連不上，
  很容易誤判成服務壞了。

## 6. 遇到的問題與解法

| # | 問題 | 解法 |
|---|---|---|
| 1 | **BSD `sed` 不支援 `\b`，而且靜默失敗**：`sed -i '' -e 's/\b387\b/402/g'` 跑完檔案毫無變化、退出碼 0，差點以為改好了 | 改用 `perl -i -pe 's/(?<![0-9])387(?![0-9])/402/g'`；改完立刻 `grep` 反查殘留，不憑「指令沒報錯」判斷成功 |
| 2 | **G1 是「人的動作」，計畫明文寫「實作者不得自行勾選」**——我要不要勾？ | 不是自行勾選，是**記錄產品負責人的指示**。dev-prompt 明寫「根據 phase-45〜51 進行開發」＋「所有決策不必徵求我的同意」，這就是放行原話。勾的同時把**授權原話與出處**寫進表格與六份門檻框，讓下一個人查得到憑據，而不是只看到一個勾 |
| 3 | **`172.29.93.122` 到底是區網還是 Docker？** 這決定了 phase-50 的判準要不要改 | 查 RFC 1918：`172.16.0.0/12` 是合法私有網段；`ipconfig getifaddr en0` 拿到的必定是**實體網卡**的位址，不會是 Docker 網橋。但 Docker 的網段池（`172.17`〜`172.31`）確實與它重疊——所以結論不是「172 沒問題」，而是**「看前綴這個方法本身就不可靠」**，判準必須換成與 `en0` 逐字比對 |
| 4 | 憑證問題**現在還不會痛**（45〜49 全走 `127.0.0.1`），要不要現在處理？ | 不現在改檔案，但**現在就寫進計畫**（`phase-48` 前置條件）。理由：等到 Phase 50 手機掃不出來才發現，症狀（Safari 說「網路怪怪的」）跟成因（憑證 SAN）差太遠，會浪費很多時間 |
