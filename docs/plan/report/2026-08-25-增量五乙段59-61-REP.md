## 一、實作邏輯

增量五要把上傳改成非同步（202＋背景 worker），但在動任何 API 契約之前，
先把「另一個行程可以呼叫的入庫函式」寫好、用測試釘死——這就是本段三個 phase：

1. **Phase 59 單圖**：新建 `app/services/ingest_job.py` 的
   `run_ingest_job(job_id, *, store, vlm, embeddings, now)`。
   不 import fastapi／celery／redis；影像從 `data/staging/` 讀（絕不進 Redis）；
   看圖＋轉向量包成一個 attempt、最多 `config.VLM_MAX_ATTEMPTS=3` 次（含第一次，
   看不懂與呼叫失敗都算）；成功走 INSERT→存原圖→縮圖→UPDATE 補路徑（失敗清半成品）、
   `photo_ids` 先寫進 job 再刪 staging 再刪 job（崩潰重送的冪等收據）；
   最終失敗＝刪 staging＋job 標 `failed`＋一句 ≤40 字的人話（不留 stack）。
   計時 log 沿用 `ai_timing.log_ai`，兩處都帶 `target=`（worker 是另一個行程，
   不帶會永遠印 backend=local）。
2. **Phase 60 PDF**：同檔加 `_run_pdf_job`——一個任務跑完整份檔（不拆成每頁一個任務）、
   每頁各自 3 次（共用 `_understand_and_embed`）、失敗跳頁、`pages_done`（含跳過）與
   `photo_ids` **同一次** `store.update` 寫入、重送從 `pages_done` 下一頁續跑、
   0 頁成功或拆不開才整筆失敗。design5 沒寫的「某頁寫檔失敗」照計畫裁決＝跳過該頁。
3. **Phase 61 建議落庫（D16）**：`_insert_photo_with_files` 多收 `entities`，INSERT 時
   一併寫 `suggested_entity`（`clamp_entity` 後的**名稱**，清單外＝NULL）、
   `suggested_task_title`（strip 後，空＝NULL）、`suggested_task_due`
   （`parse_content_time` 寬容解析，看不懂＝NULL 不擋入庫）；worker **不碰**
   entity／photo_entity／task 三表（人確認才落庫）。下游 `PhotoSummary` 五鍵→八鍵、
   `GET /folders/{id}` router 跟著帶三欄——上傳改 202 後建議只能從這裡讀，
   否則待辦窗永遠沒有入口。
