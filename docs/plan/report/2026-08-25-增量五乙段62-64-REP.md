- **真伺服器煙霧**（開發模式容器 `--reload` 已熱載新碼）：
  `POST /photos` → **202 實測 0.196 秒**（原同步 64 秒〜5 分鐘）、回應恰三鍵、
  前後 `select count(*) from photo)` 都 52（202 當下零寫入）；`GET /ingest-jobs`
  列出 queued 八鍵列＋`pending_count=10`；dismiss queued→**409**、dismiss 亂 id→**404**。
  煙霧後清掉 staging 暫存檔並觸發 reload 清空記憶體 job（正式庫零污染）。

## 四、遇到的問題與解法

1. **`test_nav_header.py::test_端點數仍為20` 也在斷言總數**——phase-64 §7 陷阱 8 說
   「全系統唯一斷言總數的是 test_ask_three_paths」，但那句寫在甲段（Phase 53）新增
   這顆之前。該測試 docstring 本來就預告「Phase 64 會變 22」，故改名
   `test_端點數仍為22` 並更新數字與沿革。
2. **計畫的三處字面 grep 驗收會誤中說明文字**（計畫自己在 phase-59 §6 就預警過這一類）：
   ① phase-62「三樣都不在了」grep 若掃全 app/ 會誤中 ingest_job.py 的**接班常數**
   `PDF_PAGE_CONTENT_TYPE`（phase-60 明文它是接班人）與歷史註解——已把 photos.py／
   schemas 掃乾淨並把 ingest_job.py 的過時歷史註解改寫成退役後的準確陳述；
   ② phase-63「camera.py 沒有 set_latest」grep 會誤中計畫**自己提供的** docstring
   「不再 `set_latest`」說明句（實際呼叫已消失）；
   ③ phase-63「photos.py 不看圖」grep 含 `ai_timing`，但 `assign_folder` 重算向量的
   embed 計時是 Phase 41 就有、且有測試釘著的行為——以「vlm 呼叫＝0」驗證意圖成立。
   另 `camera_session_service.py:42` 註解仍提到舊回應模型，但該檔依 phase-63 §4.1
   裁決**一字不准動**（留給 Phase 71 收尾）。
3. **subagent 兩處主動偏離計畫字面、經審查採納**：
   ① `test_pdf_upload.py` 的 `分頁VLM` 若沿用「第幾次呼叫＝第幾頁」會在 worker 重試下
   安靜測錯頁——改成自數頁寫法（正是 phase-60 §7 陷阱 6 預警的坑）；
   ② `test_ai_timing_log.py` 兩顆「看不懂」的 log 組數依實際重試行為改為
   `config.VLM_MAX_ATTEMPTS` 組全 ok=false（計畫「組數照舊」只在一次過時成立）。
4. 五個 subagent 並行改寫時**嚴禁它們跑 pytest**（reset_tables 會互相 TRUNCATE 測試庫），
   統一由主流程逐檔跑——13 檔改寫全數一次跑綠，並逐檔 diff 親自複審
   （無弱化斷言、無誤觸產品碼、顆數只增不減）。
