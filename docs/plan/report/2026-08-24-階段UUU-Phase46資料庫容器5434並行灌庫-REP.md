### 2.4 灌正式庫

```bash
pg_restore -h 127.0.0.1 -p 5434 -U postgres --no-owner --no-acl \
  --dbname=PersonalDocAI ~/PersonalDocAI-backup-docker遷移前.dump
```

**輸出 0 行**——沒有 `error:`、沒有 `warning:`、也沒有 `errors ignored on restore: N`。

> 計畫特別提醒：`pg_restore` **預設不會因為單筆錯誤中止，而且照樣回傳 0**，
> 所以不能只憑「指令跑完了沒紅字」判斷成功。我把輸出導到檔案後用
> `grep -c "pg_restore: error:"`（→ 0）與 `grep -c "errors ignored on restore"`（→ 0）各驗一次。

## 4. 遇到的問題與解法

| # | 問題 | 解法 |
|---|---|---|
| 1 | **`psql -f db/schema.sql` 噴 `No such file or directory`**：因為前一個指令我 `cd` 進了 `docs/plan/unfinish`，工作目錄漂掉了（`db/schema.sql` 是相對路徑） | `cd /Users/linjunting/personalDocAI` 之後重跑。計畫 §2 早就寫了「本 phase 的每一條指令都在專案根目錄執行」——這是**我沒照做**，不是計畫的問題。後續每一條 `docker compose`／相對路徑的指令都先 `cd` 到根目錄 |
| 2 | 「`pg_restore` 完全沒有輸出」一開始讓人不安——是不是根本沒跑？ | 不是。乾淨的 restore 本來就安靜。用三種方式交叉確認：① 退出碼 ② `grep` 找 `error:`／`errors ignored` 都是 0 ③ **最有力的**——G2 的 `diff` 逐字相同，37 列照片一列不差 |
| 3 | 計畫 §5.3 寫「`folder` 的 id 1〜6 種子還在」，但實際有 10 筆 | 這在階段 TTT 就查清楚了（多出來的 14／15／16／17 是使用者自建的真實資料），並已回寫兩份計畫檔。本階段驗的是「六筆種子在、收件箱唯一」，實測 `6 \| 1 \| 10` ✅ |

**沒有踩到的坑**（計畫 §8 列的八條，逐條迴避）：全程 `-h 127.0.0.1`、
