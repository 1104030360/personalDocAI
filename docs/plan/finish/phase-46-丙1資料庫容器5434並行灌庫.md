**先認識幾個名詞（第一次出現）：**

- **image（映像）／container（容器）**：image 是「打包好的程式與環境」（像光碟），
  container 是「用它跑起來的一個行程」（像用光碟開起來的機器）。
- **named volume（具名資料卷）**：Docker 自己管理、有名字的一塊硬碟空間。
  container 砍掉重建，volume 裡的資料**還在**——正式庫就住在這裡面。
  它跟 bind-mount（把 host 的某個資料夾掛進 container）不同：named volume 的實際位置由 Docker 決定，
  你不會直接用 Finder 去翻它。
- **healthcheck（健康檢查）**：Compose 定期在 container 裡跑一個指令，用它判斷
  「這個服務準備好了沒」。Postgres 用官方的 `pg_isready`。有了它，
  之後 `app` 才能宣告「等 db 健康了我再啟動」。
- **init 腳本**：官方 Postgres 映像的約定——放進 container 的
  `/docker-entrypoint-initdb.d/` 的 `.sql`／`.sh`，**只在 volume 第一次誕生時執行一次**。
  之後就算你改了那個檔，也不會再跑（這是 §8.11 最後一列的坑）。
- **`HOST:CONTAINER` 埠對應**：`"127.0.0.1:5434:5432"` 的意思是
  「把 container 裡的 5432 埠，接到**這台 Mac 的 127.0.0.1 的 5434**」。
  前面加 `127.0.0.1:` ＝只綁本機，同一個 Wi-Fi 的其他裝置**打不到**資料庫（安全）。

### 4.1 建 init 腳本

- [x] 建立資料夾與檔案 `db/docker-init/01-create-test-db.sql`：

```sql

-- 正式庫 PersonalDocAI 由 compose 的 POSTGRES_DB 建；這裡補建測試庫。
```

### 4.2 建 `compose.yaml`（只有 db）

- [x] 在專案根目錄建立 `compose.yaml`：

```yaml
# PersonalDocAI 的常駐服務定義（design4.md §8.4）。
#
# ⚠ 這一份是「開機自動拉起」用的，**永遠不要**在這裡加 uvicorn 的 --reload。
#   日常開發用 compose.dev.yaml 疊上去（Phase 49），理由見 design4.md §8.4.1。
#
# ⚠ 絕對不要跑 `docker compose down -v`：-v 會刪掉 pgdata volume ＝ 刪掉正式庫。
#   要停服務用 `docker compose stop`。

services:
  db:
    # 官方 pgvector 映像（PostgreSQL 17 ＋ vector 擴充），與本機 brew 的版本一致
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_DB: PersonalDocAI          # 容器第一次啟動時自動建這個資料庫
      POSTGRES_USER: postgres             # 官方映像強制要有帳號，用預設的 postgres
      POSTGRES_HOST_AUTH_METHOD: trust    # 不設密碼；埠只綁 127.0.0.1，區網打不到
    ports:
      # ⚠ 暫時用 5434：brew 的 postgresql@17 還佔著 5433。
      #   Phase 47 過了閘門 G2、停掉 brew 之後才改成 "127.0.0.1:5433:5432"。
      - "127.0.0.1:5434:5432"
    volumes:
      # named volume：正式庫的資料真正住的地方（container 砍掉重建也還在）
      - pgdata:/var/lib/postgresql/data
      # init 腳本：只在 pgdata 第一次誕生時跑一次；ro ＝ 唯讀掛進去
      - ./db/docker-init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      # pg_isready ＝ Postgres 官方的「你準備好了嗎」小工具
      test: ["CMD-SHELL", "pg_isready -U postgres -d PersonalDocAI"]
      interval: 5s
      timeout: 5s
      retries: 10
    restart: unless-stopped

volumes:
  pgdata:
```

> **📌 2026-08-24 code review 後對這份 `compose.yaml` 追加的三處（與上面的原文有差異，刻意的）**
> 上面那段是照 design4 §8.4 逐字抄的版本；階段 AAAA 的 code review 實測出三個問題，已補進實際檔案：
>
> 1. **檔案最上面加一行 `name: personaldocai`。** 不寫的話 Compose 拿「當前資料夾的名字」
>    當專案名，volume 就叫 `<資料夾名>_pgdata`——資料夾改名／搬家／重新 clone 成別的名字，
>    `docker compose up -d` 會**安靜地建一個全新的空 volume**、跑 initdb，
>    app 對著空資料庫起來。照片其實還在舊 volume，但看起來跟「資料全沒了」一模一樣。
> 2. **healthcheck 的 `pg_isready` 補 `-h 127.0.0.1`。** 官方映像第一次啟動時會先起一個
>    `listen_addresses=''` 的暫時伺服器跑 init 腳本，那個只聽 Unix socket；不寫 `-h` 的
>    `pg_isready` 走的正是 socket，於是 init 還在跑就回報 ready（實測早了 **22 秒**）。
>    後果：app 的 `depends_on: service_healthy` 在 volume 第一次誕生時形同虛設，
>    而且 §4.3 那個「剛看到 (healthy) 卻連線被拒」的坑就是它。加了 `-h` 之後
>    healthcheck 問的才是「TCP 真的通了沒」。
> 3. **檔頭的「不要弄丟正式庫」清單從 1 項擴成 4 項**：除了 `down -v`，還有
>    `docker system prune --volumes`／`volume prune -a`（會刪掉沒有 container 指著的具名 volume，
>    也就是任何一次 `down` 之後都危險，Docker Desktop 的 Reset／Volumes 分頁同理）、
>    `docker volume rm`、以及**把映像 tag 從 pg17 換成 pg18**
>    （pg18 的 PGDATA 是 `/var/lib/postgresql/18/docker`，掛載點不再是 PGDATA → 建新空叢集）。

```bash

```

  預期：把整份設定印出來，沒有錯誤訊息。

### 4.3 起 db（design4 §8.6 丙-1 第 2、3 步）

- [x] 只起 db：

```bash
docker compose up -d db
```

  `-d` ＝ detached（背景跑），container 起來之後終端機就還你。
  **第一次跑會先下載 `pgvector/pgvector:pg17` 映像**（幾百 MB，要網路，可能一兩分鐘，
  畫面上是一排下載進度條）——那是正常的，之後每次都秒開。

- [x] 等 healthcheck 變綠（大約 5〜15 秒）：

```bash

```

  預期：`STATUS` 欄看到 `Up X seconds (healthy)`。
  若是 `(health: starting)` 就再等一下；若是 `(unhealthy)` 或 `Exited` 就看 log：

```bash
docker compose logs db
```

> **log 裡那一大段全大寫的 `POSTGRES_HOST_AUTH_METHOD=trust` 警告是正常的**——
> 那是官方映像的例行提醒（「沒有密碼，誰連得到這個埠誰就進得來」）。我們的埠只綁 `127.0.0.1`，
> 區網打不到，所以可以忽略它。真正要找的是最後那行
> `database system is ready to accept connections`。

- [x] 確認 init 真的建了兩個資料庫：

```bash
psql -h 127.0.0.1 -p 5434 -U postgres -l
```

  預期：清單裡同時有 `PersonalDocAI`（空的）與 `PersonalDocAI_test`。

  **剛看到 `(healthy)` 就被拒絕連線（`connection refused`）？再等十幾秒重試。**
  官方映像第一次啟動時，會先起一個「只聽 container 內部 Unix socket」的暫時伺服器來跑 init 腳本，
  這段期間 container 裡的 `pg_isready` 就已經回報成功、healthcheck 會提早變綠，
  但這時 5434 還沒真的開始聽。判斷方式：`docker compose logs db` 裡
  `database system is ready to accept connections` 會出現**兩次**，**第二次**那行才是正式的。

> **`-h 127.0.0.1` 不能省**：不寫 `-h` 時 psql 會走 Unix socket（本機檔案）連線，
> 那會連到 brew 的那一套，不是 Docker 的。**只要是打 Docker 這一邊，一律寫 `-h 127.0.0.1`。**

## 8. 常見陷阱

1. **忘了 `-h 127.0.0.1`**：`psql -p 5434 …` 沒有 `-h` 時走的是 Unix socket，
   會連到 brew 那一套（而且很可能連得上、只是資料不對），然後你會對著錯的資料庫查半天。
   **打 Docker 一律加 `-h 127.0.0.1`。**

2. **`docker compose down -v`**：`-v` 刪 volume ＝ 刪資料庫。
   這個階段刪掉還救得回來（正本在 brew），Phase 47 之後就是災難。
   養成習慣：停服務用 `docker compose stop`，不要用 `down`。

3. **改了 init 腳本卻沒效果**：官方映像的 init 腳本**只在 volume 第一次誕生時跑**。
   改完要生效就得砍掉 volume 重來（§5.4 第 ② 步）——但那要在 G2 之前才安全。
   design4 §8.11 最後一列也講了替代方案：測試庫直接用 `psql -f db/schema.sql` 補。

4. **用 `postgres:17` 而不是 `pgvector/pgvector:pg17`**：官方純 Postgres 映像**沒有** vector 擴充，
   `pg_restore` 灌到 `CREATE EXTENSION vector` 那一行就會炸。G2 的 extension 檢查就是抓這個。

5. **在 compose 裡先把 `app` 寫好**：`Dockerfile` 還不存在，`docker compose config` 會過
   （它不檢查檔案存不存在），但之後任何一個 `docker compose up`（不指定服務名）都會去 build 而失敗。
   本輪就只寫 db，Phase 48 再加。

6. **忘了測試庫**：`pg_restore` 只灌正式庫。測試庫是空的資料庫（init 建的），
   **裡面沒有任何表**——不補 `schema.sql` 的話，Phase 47 換完 URL 後 `pytest` 會整套紅。

7. **把 5434 當成最終狀態**：不是。5434 只是這一輪的臨時借位，
   Phase 47 會改回 5433。別把它寫進 `.env` 或任何文件裡。

8. **volume 名稱猜錯**：Compose 會幫 volume 加上專案名前綴（通常是資料夾名，
   所以是 `personaldocai_pgdata`）。要刪之前先用 `docker volume ls` 看清楚實際名稱。
